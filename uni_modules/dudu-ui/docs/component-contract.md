# 组件契约与扩展路线

## 一个组件的交付单元

`components/du-name/` 中包含同名 `.uvue`、`component.json` 和 `readme.md`。元数据驱动组件目录和示例入口，状态从 experimental 开始。源码只能依赖插件内部文件及框架官方模块，不依赖示例工程或浏览器全局对象。Web 专属 DOM 适配必须放在 WEB 条件编译分支。

在开发仓库运行 `npm run component:new -- badge` 可创建 `du-badge`、示例路由和文档入口。生成器拒绝覆盖已有组件；生成后仍需实现真正的 API 和交互。不要创建只有名字的完整组件目录。

## API 规则

- 受控输入类使用 `modelValue` / `update:modelValue`，父级是唯一数据来源；不传受控值时 defaultValue 只初始化非受控状态；输入组件不内置业务校验器。
- props 描述状态和外观，events 描述用户动作；事件参数在文档中固定。禁用和加载必须阻止重复提交。
- required、默认值、可选值、事件载荷、样式入口、平台差异必须文档化。避免万能 options 和不透明 JSON 对象。
- 使用官方原生组件保留输入、滚动和按钮行为，平台限制允许时才增加插槽。按钮 label 与默认/命名 slot 均可用；原生组合路径保留独立的原生按钮点击面，slot 文字由消费方显式设置。
- class/style 用于根节点，externalClasses 用于明确的内部节点。内部结构与私有 class 不作为公共 API。
- 异步请求、路由、权限、业务校验属于消费方。库不接管网络或宿主全局生命周期。
- 删除/重命名稳定 API 属于破坏性更新，需要版本变更、迁移说明和回归示例；实验 API 也必须记录变更。

## 能力范围与建设顺序

以 Tamagui 的组件、属性和组合能力作为目标。开发仓库 `docs/tamagui-parity.md` 记录官方来源与逐项范围，Beads Epic `du-bz6` 管理实际工作及依赖。首先完成公共尺寸/主题/状态/组合契约，再推进基础组件、表单、焦点/浮层、复合交互，最后逐端稳定和市场发布。

当前 Button 已支持图标与插槽、状态样式、数值/token 尺寸及表单语义；Input 已支持受控和非受控初始化及平台输入属性；Provider 提供局部配置与默认值。三个组件仍为 experimental，后续增加能力须保持已有 API 的兼容并执行逐端验收。

每个组件完整交付 API 类型/默认值/事件/组合节点/差异文档、可运行示例和逐端证据。原生暂不支持的能力必须写明替代方案与证据；只建立任务或生成目录不算实现。

## uni-app X 性能边界

默认样式隔离、简单 class 选择器、Flex 布局、显式文字样式。交互节点不 flatten。长列表遵守官方 list-view / list-item 同文件及稳定 key 的复用条件，不能为了封装破坏复用。原生 API 集成才引入 utssdk；不先写跨端代理层。性能结论必须附设备、编译版本、release 构建、数据量和测量方法。

## 稳定与发布

新增组件经过 `check`、工具测试、相关 Web 与 App 编译、交互回归及独立消费者验证。稳定状态需要目标平台的运行证据与 API 审查；当前三个参考组件均为 experimental。

发布只包含 `uni_modules/dudu-ui`。示例、生成脚本和宿主配置不进入插件。许可证、作者和目标平台证据齐备后才执行首次市场发布，未验证平台保持未验证标记。
